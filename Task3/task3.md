# Task3 – Переход на Event-Driven архитектуру

## 1. Проблемы текущей архитектуры

### 1.1. Синхронные REST-вызовы к ins-product-aggregator

- core-app и ins-comp-settlement получают данные о продуктах и тарифах через синхронный REST.
- При каждом вызове ins-product-aggregator ходит во все подключённые страховые компании (сейчас 5, скоро 10).
- Любая задержка или ошибка во внешнем API блокирует ответ whole-chain:
    - увеличивается время ответа;
    - растёт вероятность таймаутов и 5xx для запросов core-app / ins-comp-settlement.
- При росте числа страховых компаний время ответа и частота ошибок будут увеличиваться.

### 1.2. Периодический опрос (polling) и устаревшие данные

- core-app опрашивает ins-product-aggregator раз в 15 минут и хранит локальную реплику продуктовых данных.
- ins-comp-settlement опрашивает ins-product-aggregator раз в сутки (ночью).
- Данные могут быть устаревшими до 15 минут / 1 суток:
    - пользователи могут видеть неактуальные продукты/тарифы;
    - взаиморасчёты строятся по старым тарифам.

### 1.3. Нагрузочные пики и ночное окно

- Ночной запрос ins-comp-settlement к ins-product-aggregator потенциально тяжёлый (все продукты/тарифы).
- При увеличении числа страховых (до 10) ночное окно может занимать значительное время.
- Любые ошибки ночью требуют ручного вмешательства и повторных прогонов.

### 1.4. Жёсткая связанность и каскадные отказы

- core-app и ins-comp-settlement жестко завязаны на доступность ins-product-aggregator и core-app.
- Если ins-product-aggregator недоступен, core-app не может актуализировать продукты.
- Если core-app недоступен ночью, ins-comp-settlement не получает список полисов.
- Отказ одного сервиса ломает бизнес-процесс целиком (подбор продуктов, взаиморасчёты).

### 1.5. Дублирование данных и риск рассинхронизации

- core-app и ins-comp-settlement держат свои локальные реплики продуктовых данных.
- При ошибках взаимодействия REST возможна рассинхронизация:
    - в одном сервисе данные обновились, в другом – нет.
- При увеличении числа страховых и сложных продуктовых моделей риск рассинхронизации возрастает.

### 1.6. Ненадёжный nightly-процесс взаиморасчётов

- ins-comp-settlement раз в сутки:
    - тянет продукты и тарифы из ins-product-aggregator;
    - тянет оформленные полисы из core-app.
- Любой сбой (таймаут, ошибка сети, падение сервиса) приводит к:
    - пропуску части данных или дублированию записей;
    - срыву сроков взаиморасчётов и ручным корректировкам.

## 2. Предложенное Event-Driven решение

### 2.1. Общая идея

- Вводится **Event Bus / Message Broker** (Kafka / Yandex Data Streams / MQ).
- Ключевые изменения переводятся с REST-polling на **event streaming**.
- REST остаётся там, где требуется синхронный ответ пользователю (frontend, B2B).

### 2.2. Взаимодействия, переведённые на события

#### Актуализация продуктов и тарифов

- ins-product-aggregator периодически или по триггерам получает данные от страховых и обновляет свою БД.
- После успешного обновления он публикует события в брокер (топик `product-updates`), например:
    - `ProductCreated`
    - `ProductUpdated`
    - `TariffUpdated`
- core-app и ins-comp-settlement подписаны на `product-updates` и обновляют свои локальные реплики асинхронно.
- Регулярный REST-поллинг (`core-app → ins-product-aggregator` каждые 15 минут, `ins-comp-settlement → ins-product-aggregator` раз в сутки) становится ненужным и убирается.

#### Оформленные страховки (полисы)

- При оформлении, изменении или отмене полиса core-app:
    - сохраняет изменения в собственной БД;
    - публикует события в брокер (топик `policy-events`):
        - `PolicyCreated`
        - `PolicyUpdated`
        - `PolicyCancelled`
- ins-comp-settlement подписан на `policy-events` и:
    - получает события в режиме near-real-time;
    - накапливает данные о полисах в своей БД;
    - ночной процесс взаиморасчётов использует локальные данные, без обращения к REST API core-app.

### 2.3. Где остаётся REST

- frontend ↔ core-app – синхронные запросы пользователей (подбор продуктов, оформление полисов).
- B2B клиенты ↔ core-app / API Gateway – синхронный B2B API.
- ins-product-aggregator ↔ страховые компании – REST / SOAP / GraphQL по условиям внешних партнёров.
- core-app ↔ ins-product-aggregator – опционально остаётся REST-запрос для некоторых online-калькуляций (например, единичные котировки ОСАГО), но не для периодической синхронизации продуктовых справочников.

## 3. Transactional Outbox

Для надёжной публикации событий используется паттерн **Transactional Outbox**.

### 3.1. Где применяется

- **ins-product-aggregator**
    - При обновлении продуктов и тарифов в БД сервис в одной транзакции:
        - записывает изменения в доменные таблицы;
        - записывает соответствующие события в таблицу `outbox`.
    - Отдельный компонент (outbox-relay) читает таблицу `outbox` и публикует события в Event Bus (`product-updates`), помечая успешно отправленные записи.

- **core-app**
    - При создании / изменении полиса:
        - записывает изменения в таблицы полисов;
        - записывает события (`PolicyCreated`, `PolicyUpdated`, `PolicyCancelled`) в таблицу `outbox`.
    - Outbox-relay публикует эти события в Event Bus (`policy-events`).

### 3.2. Зачем это нужно

- Избежать проблемы «dual write» (два независимых коммита в БД и брокер).
- Обеспечить атомарность на уровне одного сервиса:
    - если транзакция в БД не закоммитилась – события не появится в outbox;
    - если брокер временно недоступен, события не теряются, а висят в outbox до успешной отправки.
- Гарантировать целостность интеграций и корректность данных в core-app и ins-comp-settlement.

## 4. Изменения на диаграмме контейнеров

На обновлённой диаграмме контейнеров InsureTech добавлено:

1. **Event Bus / Message Broker**
    - От ins-product-aggregator к Event Bus: события `product-updates` (producer).
    - От Event Bus к core-app и ins-comp-settlement: потребление `product-updates` (consumers).
    - От core-app к Event Bus: события `policy-events` (producer).
    - От Event Bus к ins-comp-settlement: потребление `policy-events` (consumer).

2. Внутри `core-app` и `ins-product-aggregator` показан паттерн **Transactional Outbox**:
    - запись доменной сущности + запись события в outbox в одной транзакции;
    - отдельный процесс/компонент отправляет события в брокер.

3. Убраны или помечены как legacy:
    - периодические REST-запросы `core-app → ins-product-aggregator` (каждые 15 минут);
    - периодические REST-запросы `ins-comp-settlement → ins-product-aggregator`;
    - nightly REST-запрос `ins-comp-settlement → core-app` для получения списка полисов.
